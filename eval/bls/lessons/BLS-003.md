**Expected composite factor:** `1.5650` (56.50% escalation)

## BLUF: Problem, Mitigation, Effect, Conclusion

**Problem:** Earlier BLS evaluations revealed that agents could select economically relevant PPI subseries lacking observations for the requested historical base period. In two GPT-5.4 episodes, selection of a narrower gypsum series resulted in failed escalation calculations. Although the calculation tool correctly rejected unavailable observations, the agent did not successfully recover. The existing specification-validation workflow did not adequately identify this problem before calculation.

**Mitigation:** Added snapshot-backed historical observation availability checks to `validate_index_spec`. The validation process checks whether selected series have usable observations for the requested base and target periods, consistent with the calculation service's period-alignment rules. When required observations are unavailable, validation returns an explicit `SERIES_PERIOD_UNAVAILABLE` finding rather than permitting the specification to proceed without warning. This is a production MCP tooling change. No public tool schema, evaluation scenario, grader, or numerical oracle was intentionally modified.

**Effect:** Following the change, GPT-5.4 passed 3/3 evaluation episodes and GPT-5.6 Luna passed 2/3, for a combined 5/6 complete passes (83.3%). All 18 guardrail checks passed. The single failed episode involved a repeated confirmation loop that prevented validation and calculation. The model runs therefore demonstrate continued successful execution of valid escalation workflows but do not independently establish that the new availability check prevents calculations using unavailable historical observations.

**Conclusion:** Retain the targeted validation improvement provisionally, subject to confirmation of focused regression-test results. The unchanged evaluation fingerprint supports comparison of overall workflow outcomes, but the model evaluations do not isolate the effectiveness of the new availability check. BLS-003 remains partially verified. A targeted regression test or future evaluation should deliberately submit an unavailable series-period combination and verify that validation identifies the problem before calculation.

## 1. Original Observed Failure

### Evaluation context

The issue was identified during BLS-002A evaluations of `commodity-series-selection`.

The scenario requires an escalation calculation using three PPI components:

| Component | Weight | Expected series |
|---|---:|---|
| Fabricated structural metal | 60% | `PCU332312332312` |
| Ready-mix concrete | 25% | `PCU327320327320` |
| Gypsum manufacturing | 15% | `PCU327420327420` |

The calculation uses:

- Base period: 2014 annual average.
- Target period: 2026 annual average.
- Fixed component weights totaling 100%.
- Expected composite escalation factor: `1.5650`.
- Expected percentage change: 56.50%.

### Observed behavior

During the post-ranking BLS-002A evaluation, GPT-5.4 selected the narrower gypsum series `PCU327420327420P` in two of three episodes.

That series lacked the required 2014 annual-average observation in the synthetic snapshot.

The agent attempted escalation calculations using the unavailable series. The calculation tool rejected the request because the necessary historical observation was missing.

The agent did not successfully recover to an appropriate available series, and both episodes failed their required process, accuracy, and format checks.

### Initial failure classification

The calculation tool behaved appropriately by refusing to fabricate missing observations.

The underlying workflow weakness was that historical observation availability was not sufficiently enforced during specification validation.

This allowed an agent to proceed toward calculation with a specification that could not produce the requested escalation.

The observed failure therefore justified investigation of the validation layer rather than weakening calculation safeguards.

## 2. Root-Cause Analysis

### Confirmed observations

The earlier evaluations established that:

1. A textually relevant series could lack observations for the requested escalation period.
2. Agents did not consistently recognize this limitation before calculation.
3. The calculation service rejected missing observations rather than fabricating data.
4. Recovery from the resulting calculation failure was inconsistent.

### Root-cause hypothesis

The specification-validation workflow did not sufficiently incorporate snapshot-backed historical observation availability.

Consequently, a specification could satisfy structural requirements while still being unsuitable for the requested historical calculation.

### Classification

**Primary classification:** Production MCP validation deficiency.

**Contributing behavior:** Model series selection and incomplete error recovery.

**Not established:** A defect in the calculation engine's arithmetic or missing-data safeguards.

## 3. Implemented Mitigation

### Production change

Updated the BLS specification-validation workflow to check historical observation availability against the configured DuckDB snapshot.

The intervention covers:

- Availability of observations for the requested base period.
- Availability of observations for the requested target period.
- Period handling consistent with existing calculation alignment rules.
- Explicit validation findings when required observations are unavailable.

The validation layer is connected to the existing snapshot-backed data services.

### Expected validation behavior

For a specification containing a series without the required historical observation, validation should report:

`SERIES_PERIOD_UNAVAILABLE`

The finding should identify the unavailable series-period combination and provide actionable guidance.

The agent should then select an appropriate alternative, explain the substitution, and obtain any necessary user approval before proceeding.

The system must not silently replace the selected series or fabricate observations.

### Change boundaries

The mitigation does not intentionally modify:

- Public MCP tool request or response schemas.
- PPI or ECI observations.
- Series hierarchy relationships.
- Escalation formulas.
- Existing evaluation scenarios.
- Simulated-user behavior.
- Deterministic numerical oracles.
- Existing guardrail expectations.

## 8. Regression Risks

### Availability-check correctness

The validation layer must distinguish genuinely unavailable observations from periods that can be handled through existing frequency-alignment rules.

Incorrect availability checks could reject valid specifications.

### Performance

Snapshot-backed availability checks introduce additional database operations during validation.

The impact on validation latency has not been separately quantified.

### Model recovery

An explicit validation error does not guarantee that an agent will choose an appropriate replacement.

Agents may repeatedly submit invalid specifications, abandon calculations, or change approved series without authorization.

### Confirmation consistency

The failed GPT-5.6 episode demonstrates that confirmation-loop behavior remains possible even when the underlying series selection is correct.

### Economic suitability

Historical availability is necessary for a valid escalation calculation but does not establish economic suitability.

A series may contain observations for both periods while still being inappropriate for the cost component.

### Regression coverage

The existing nine evaluation scenarios should remain frozen during controlled MCP comparisons.

Additional scenarios should be justified by observed failures or documented regression risks and introduced separately.

## 9. Comparability and Evidence Limitations

The BLS-003 and preceding BLS-002A model runs used the same evaluation fingerprint, system-prompt fingerprint, and synthetic snapshot.

This supports comparison of the observed episode outcomes.

However, the runs involved only three repetitions per model.

Differences in pass rates may reflect stochastic model behavior rather than a causal effect of the production change.

The current model evaluation also does not deliberately force selection of an unavailable historical series.

Therefore, the BLS-003 results cannot independently establish the effectiveness of the new availability-validation behavior.

The strongest direct verification should come from focused deterministic regression tests that exercise missing-observation cases.

## 10. Outcome and Disposition

**BLS-003 disposition: Partially verified; retain provisionally.**

The production change addresses an observed weakness in the specification-validation workflow.

The post-change model evaluations demonstrate that valid escalation workflows continue to complete successfully in five of six episodes.

The sole failed episode was attributable to a confirmation loop rather than historical observation availability.

The evidence does not demonstrate improved overall episode completion or directly verify model recovery from unavailable historical observations.

### Recommended follow-up

A future targeted evaluation should deliberately construct a specification containing a series that lacks the requested historical observation.

It should verify that:

- Validation identifies the missing observation.
- The agent does not proceed with an invalid calculation.
- The agent identifies a defensible alternative.
- Any substitution receives required user approval.
- The final calculation uses verified observations and preserves provenance.

This scenario should be queued separately rather than modifying the existing nine-case evaluation baseline.
